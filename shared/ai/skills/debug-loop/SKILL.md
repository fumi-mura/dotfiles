## 使うタイミング

- 「まだ直っていない」「再発した」と言われたとき
- 同じ症状に2回目の修正を入れようとしているとき
- 症状の原因に確信がないまま実装に入りそうなとき

## 鉄則

1. **再現手順が揃うまで直さない**
2. **仮説は1つずつ、できるなら計測で確かめる**
3. **2回外したら実装を止めて、切り分けに戻る**

もっともらしい原因を見つけただけで直すのが最大の失敗パターン。その原因が**報告された現象をそのまま説明できるか**を必ず確かめる。説明できないなら、それは別のバグ。

## 手順

### 1. 症状を確定させる

次の5点のうち、足りないものだけを聞く（全部を質問形式で並べない）。

- どの画面
- 操作の順番
- 実際に起きたこと
- 期待する結果
- 確認した環境（実機／シミュレーター、ビルドの新しさ）

聞き方の例:

```
どの操作で起きるか、順番を1行で教えてください。
例）テロップを右端までドラッグ → 枠は止まる → さらに右へ動かすと文字だけ動く
```

見た目の話で言葉にしづらいときはスクリーンショットを頼む（保存先: `~/ScreenShot`）。

### 2. 「直っていない」の切り分けを先にやる

原因探しの前にこの順で潰す。飛ばすと空回りする。

1. **新しいビルドが入っているか。** 自分が実行しているのはシミュレーターのビルドで、ユーザーの実機アプリは別物
2. **その環境で再現するか。** 実機でしか出ない領域（下記）に該当しないか
3. **前提が変わっていないか。** 設定、保存データ、キャッシュ、権限

### 3. 原因を計測で特定する

- ソースを読んで**仮説を1つ書く**
- 数値で確かめられるものは確かめる。一時的なテストを書いて実測値を print し、確認後に削除する
- 同じ値を2つの経路で計算していないか疑う（プレビューと書き出し、UIと保存値など）。基準の不一致は「少しだけずれる」症状の定番
- 経路を全部 grep する。削除・リネームの前は特に、テストコードも含めて

### 4. 直す

- 先に失敗するテストを書く（座標計算・レイアウト・状態遷移はテストにできる）
- 直すのは特定した原因だけ。ついでの修正を混ぜない
- 全テストを通す

### 5. 報告する

- 原因（1〜2行）
- 直した箇所（`file:line`）
- **どこまで検証したか**。「シミュレーターでビルド＋テスト通過／実機の触覚は未検証」のように未検証を隠さない
- 実機確認が必要ならそう書く

## シミュレーターで検証できないもの（iOS）

該当したら必ず実機確認を依頼する。

- 触覚（`UIFeedbackGenerator` / Core Haptics）
- カメラ・マイク・`AVCaptureSession`・`AVAudioSession` の実挙動
- 位置情報の実測
- 書き出しやエンコードの速度、発熱、メモリ
- Face ID、通知、課金

触覚が鳴らない場合、`AVAudioSession` が録音モードだと iOS 側で無音化される点も疑う（`setAllowHapticsAndSystemSoundsDuringRecording(true)`）。

## 2回外したら

実装を止めて、次のどれかに切り替える。

- 操作の順番か短い動画をユーザーに頼む
- 計測用のログを一時的に足して数値を出す
- 「AとBのどちらの挙動を見ていますか」と、**結果の形**で確認する

## 曖昧な要望の扱い

1行の要望が2通りに読めるときは、解釈を選んで実装せず、**結果の形**で確認する。

```
「編集中は常に中央に」
→ 左寄せのテロップをタップしたとき、文字は
  A: 画面の中央に出る
  B: 元の位置の真上に出る
  どちらですか
```

外れると作業がまるごと無駄になる。実装より確認1回の方が安い。

## 外部アプリを参考にするとき

「Instagram と同じにしたい」のような要望は、**記憶で挙動を断定しない**。スクリーンショットをもらうか、認識を箇条書きにして先に確認を取る。間違った前提で作った仕様は、実装ごと捨てることになる。
