## 使うタイミング

- 「リファクタして」「重複を整理して」「コードを見直して」と言われたとき
- 対象は引数で指定できる（手順0）。バグ修正・機能追加・仕様変更は対象外

## 鉄則

1. **挙動を変えないことが最優先。** 効果より優先する。変わらない確信がなければ、やらないか確認する。迷ったら変えない
2. **危ない変更・ハイリスクハイリターンな変更は、自分で判断せず確認する**（「確認する条件」）
3. 疑わしい挙動（バグの疑い）は直さず報告する
4. 「保証」はできない。検証した範囲と未検証の範囲を書く。型チェックが通っただけでは検証済みとしない
5. 調査と修正を分ける。一覧を見せて、選ばれるまで変更しない
6. 1件ずつ小さく。1件ごとにビルド・テスト・出力比較をし、赤なら戻す
7. テストが無い箇所は、先に現状を固定するテストを書く。書けなければ対象外
8. 既存テストの期待値は変えない。変えないと通らないなら挙動が変わっている証拠なので中止する

## 手順

### 0. 範囲

引数にパス（複数可）を指定できる。例: `/refactor Sources/Foo Sources/Bar.swift`

- 指定あり: そのパスだけが調査・変更の対象（フォルダは配下すべて）。存在しないパスは推測せず確認する
- 指定なし: リポジトリ全体（生成物、依存物、ロックファイルを除く）。大きければ領域ごとに1つずつ
- 対象外は変更しない。読むのは可。変更が対象外へ波及するなら確認する

### 1. ベースライン

1. `git status` を確認する。未コミットの変更はユーザーの作業なので、上書き・巻き戻しをしない
2. ビルドとテストを実行し、全て通ることと件数を記録する（コマンドは README、AGENTS.md、Makefile 等から特定）。赤なら止めて報告する
3. 出力が決定的なら、変更前の出力を保存する（README や docs の「決定的」「ゴールデン」「スナップショット」が手がかり。無ければ聞く）

### 2. 調査（変更しない）

`file:line` の根拠付きで、読んで確かめられたものだけ挙げる。

- **重複**: コピペ、ほぼ同一の型・関数
- **簡素化**: 長い関数、深いネスト、不要な分岐、デッドコード（参照ゼロを確認）、1実装だけの抽象
- **効率**: 不要な再計算、ループ内の重い処理、不要なコピー。推測なら「未計測」と書く
- **抽象度**: 責務の混在、抽象度が同居した関数、層の逆流、命名と責務の不一致

各指摘: ID、観点、場所、要約、効果（大/中/小）、リスク（低/中/高）、検証方法、テストの有無、要確認。

- 低: 名前変更、関数抽出、参照ゼロの削除、同一コードの共通化
- 中: 条件式の書き換え、公開API、評価順や副作用の順序が絡むもの
- 高: 並行処理、エラー処理、永続化形式、浮動小数の計算順、初期化順、動的・文字列参照で使われうるもの

効果順の表で提示する。要確認の項目は別枠にし、理由と選択肢（見送る／検証を足して進める／そのまま進める）を添える。効果が小さくリスクが高い項目は挙げず見送る。バグの疑いは「参考」として別枠にする。**ここで止まり、選んでもらう。**

### 3. カバレッジ

選ばれた項目ごとに、範囲を通るテストがあるか確認する。無ければ、現状の出力を固定する特性テストを**変更の前に**書いて緑にする（期待値は現状の挙動）。書けなければ対象外にして報告する。テスト追加も変更なので、事前に伝える。

### 4. 1件ずつ適用

1. 触るファイルをリポジトリ外（`mktemp -d`）へ退避する
2. 変更する。ついでの修正や挙動を変える修正は混ぜない
3. ビルド、テスト、出力比較を実行する
4. 全て緑で差分なしなら完了。赤か差分ありなら退避から復元し、原因を1回だけ調べ、直らなければ見送る
5. 要確認の項目は、選択済みでも適用の直前に差分の要点とリスクを示して再確認する
6. 作業中に新たなリスク（想定外の呼び出し元、動的参照、検証手段の不足）が見つかったら、止めて確認する

名前変更に伴うテスト内の参照更新は可。アサーションと期待値は変えない。

### 5. 最終検証

全体のビルド、テスト、出力比較を再実行する。テスト件数がベースライン以上であること、`git diff --stat` に意図しないファイルが無いことを確認する。

### 6. 報告

- 適用した項目（ID、`file:line`、要旨）と、見送った項目（理由）
- 検証した内容: ビルド、テスト件数（前→後）、出力比較の対象と結果
- **検証できていない範囲**: テスト外の分岐、UI・実機、並行処理のタイミング、性能など
- 未修正のバグの疑い
- コミットはしない。指示を待つ

## 確認する条件

次のどれかに当てはまれば、自分で判断せず必ず確認する。

- リスクが高い（効果に関係なく）
- ハイリスクハイリターン（効果が大きくても確認を省かない）
- 挙動が変わらないと言い切れない（目視のみ、範囲を通るテストや出力比較が無い）
- 公開API、永続化形式、外部が依存する文言に触れる
- 変更が広範囲、または呼び出し元を網羅できていない
- 指定した対象の外へ波及する
- 想定外の事態（復元しても原因不明、ベースラインが赤、意図しないファイルの変更）

確認では、変更内容、起きうる影響、検証方法（またはできないこと）、選択肢と推奨を短く示す。低リスクで検証が揃った項目は、まとめて選んでもらってよい。

## 挙動保存の検証手段（強い順）

1. 既存のビルドとテスト
2. 特性テスト
3. 出力比較（バイト列、ハッシュ、`--json`、フォーマッタやシリアライズの出力）
4. 公開シグネチャの差分、静的解析の警告数
5. 目視レビュー（これだけでは検証済みと書かない）

## 挙動が変わりやすい書き換え

評価順・短絡評価・副作用の順序 / 浮動小数の計算順と丸め / 型変換・オーバーフロー / 例外の種類・メッセージ・発生時期 / 並行処理・スレッド境界 / 初期化タイミング / ソートの安定性・辞書の順序 / リフレクション・文字列参照・シリアライズのキー名 / 外部が依存するログ文言

## やらないこと

- `git commit`、`push`、`reset`、`checkout --`、`clean`、`stash`（ロールバックは退避コピーから）
- 挙動を変える修正、テストの期待値の変更
- 未計測の性能最適化、必要性のない依存追加・設定変更
